# Antifraud и переключатель идемпотентности Audit

## Прямо запрошенные локальные правки

- Ошибка Antifraud 503 не создаёт платёж; красная плашка объясняет невозможность создания и причину.
- Удалить ручной повтор события из карточки; кнопку случайных данных не добавлять.
- В карточке сервиса Antifraud состояние бизнес-проверки отражает выбранный режим, а не только успешный GET /admin/status.
- После уточнения 29 октября slow = 60000 мс, затем HTTP 503 в контроллере; read timeout Payment = 900 мс. Значения брать из конфигурации.
- Блокировки сохраняются: защищают одновременное подтверждение одного платежа, а не доставку Kafka.

## Audit: согласованное изменение схемы

Проверено в живой PostgreSQL: audit_entries_event_id_key = UNIQUE(event_id).
Он не позволит сохранить пять одинаковых событий даже при отключении проверки в Java.

### Варианты

1. Рекомендуемый: отдельный журнал обработанных eventId. UNIQUE переносится в новую служебную
   таблицу; записи Audit допускают одинаковый eventId. В одной транзакции отмечаем eventId и
   сохраняем факт. При включённой защите повтор игнорируем; при выключенной — сохраняем каждую
   доставку. Журнал eventId поддерживаем в обоих режимах, чтобы после включения защиты уже
   встречавшееся событие снова не записалось. Это обычная демонстрация Idempotent Consumer.
2. Условный deduplication_key в той же таблице: меньше SQL, но специальная nullable-колонка и
   отдельные правила переключения делают учебный код менее очевидным.

### Последствия рекомендуемого варианта

- Добавится служебная таблица eventId; она заполнится из текущего Audit.
- У существующей таблицы снимется только UNIQUE(event_id); первичный ключ id сохраняется.
- Старые платежи, факты, eventId и timestamps не изменяются; строки не удаляются.
- По умолчанию защита включена. Runtime-переключатель в «Сервисы → Audit» не делает DDL.
- Пять копий одного события: включено — одна запись, выключено — пять записей с тем же eventId.
- Включение защиты обратно не удаляет ранее созданные дубли, но не добавляет новые эффекты для уже встречавшегося eventId.
- Нужны проверка миграции на существующих данных, повторного запуска, rollback/retry и конкурентных доставок.
