# Payment Platform — предложение правок для согласования

**Статус:** историческое предложение. Владелец явно одобрил продолжение 26.10.2026 с уточнениями:
пять вкладок, форма на обзоре, отдельные Сервисы/Аудит, CARD/QR строго больше 100000 → отказ.
Текущий согласованный вариант: [спецификация](superpowers/specs/2026-10-26-payment-console-approved.md),
реализованный интерфейс и запуск: [README](../README.md). Ниже сохранён исходный предмет обсуждения.

## 1. Что меняем в интерфейсе

Предлагаются три вкладки: **Обзор · Платежи · API**.

### Обзор

- Три компактные карточки: Payment :8081, Antifraud :8082, Audit :8083.
- На карточке: доступен ли HTTP API, порт, короткое текущее состояние.
- У Audit отдельно различать «HTTP доступен», «Kafka consumer активен» и «consumer на паузе».
- По нажатию: текущие настройки, без длинного списка счётчиков на главном экране.
- Ниже — последние платежи. Общую техническую ленту с SQL/Redis/HTTP с обзора убрать.

### Платежи

- Список всех платежей с поиском и фильтром по статусу; не ограничиваться только последними 20.
- В строке: номер, владелец, сумма, способ оплаты и статус.
- Создание через Swagger должно появляться в списке без перезагрузки страницы.
- В карточке: сумма, тип, статус, владелец, причина отказа и история изменений.
- Историю брать из БД Audit с фильтром по paymentId, не из общей ленты последних 100 событий.
- Пустую историю отличать от недоступности Audit.
- SQL, query count, скорость ответа, ключи Redis не показывать как отдельные блоки интерфейса.

### API

- Три раскрывающихся раздела: Payment, Antifraud, Audit; открыт один Swagger за раз.
- Настоящий Swagger каждого backend: описание HTTP endpoints, JSON, Execute и фактический ответ.
- Payment: создать, прочитать, подтвердить и повторно отправить событие.
- Antifraud: вызвать проверку и посмотреть решение; отдельно — настройки имитации отказов.
- Audit: получить историю конкретного платежа; отдельно — пауза/resume для показа Kafka.
- Для начала предлагается штатный Swagger, без разработки собственного API-клиента.
- Выбор: убрать UI-форму создания либо сохранить как дополнительный быстрый способ.
  Рекомендация: при проверке создавать через Swagger; сама форма не нужна для объяснения HTTP.

### Что удалить

Lab / «Лабораторию», её карточки сценариев и кнопки «показать проблему / исправить»;
LOCAL PLAYGROUND; подпись про учебное окружение; баннер с инструкцией запуска shell-скрипта.
Убрать общую техническую ленту с обзора. При этом не удалять код N+1, кэша и retry:
он нужен для самостоятельного показа в IDE/API.

## 2. Платёж и Antifraud — выбрать механику

Способы оплаты: CARD, QR, INSTALLMENT, RECURRENT. Это свойство платежа, а не его статус.
Правила Antifraud должны учитывать тип и сумму; конкретные пороги ещё не согласованы.
Пример для обсуждения: одна сумма проходит для CARD и получает отказ для RECURRENT.
Правила подписываются как учебные, не как настоящая банковская модель риска.

**Вариант А — проще, рекомендован для первого прохода:**
POST создаёт NEW либо REJECTED после HTTP-проверки; отдельный confirm переводит NEW в CONFIRMED.
Отказ остаётся в списке с причиной. Нет искусственного автоматического процессинга.

**Вариант Б — нагляднее этап проверки, больше кода:**
NEW → CHECKING → READY / REJECTED → CONFIRMED. Нужно отдельно решить, чем запускается проверка:
отдельным запросом или асинхронной обработкой. Статусы не должны просто переключаться таймером в UI.

Недоступность Antifraud (503/timeout) не приравнивать к отрицательному бизнес-решению.
Как хранить такой незавершённый платёж, если выберем вариант Б, также согласовать.

## 3. Kafka и Audit

- Хранить создание платежа, отказ и подтверждение как отдельные факты.
- Для факта: eventId, paymentId, время, тип события, статус и причина решения.
- Отправлять только после успешного commit БД.
- В карточке показывать сохранённые бизнес-факты, а не каждый SELECT и служебный GET.
- Повтор того же события сохраняет eventId; Audit не создаёт вторую запись.
- Показать отставание Audit при паузе consumer и получение истории после resume.
- Outbox сейчас не добавлять. Без него нельзя обещать атомарность commit БД + публикации Kafka;
  ограничение явно описать, не выдавать этот пример за готовую финансовую систему.

## 4. Организация кода и запуск

- contracts → common-libs, понятное название Common Libs. Не переносить туда все DTO подряд:
  только действительно общие запросы, ответы и Kafka-контракты.
- Решить отдельно: нужно ли вообще переименовывать служебные lab пакеты/HTTP endpoints в admin.
  Удаление Lab-экрана не требует такого переименования; ради одного названия оно необязательно.
- Сохранить Gradle, application.yml, текущие Make-команды и запуск Java вне Docker.
- Для маленькой Java-правки: make rebuild-payment. Это не сборка Docker-образа и не перезапуск соседей.
- В черновике есть запрос на ограничения памяти контейнеров: предложить бюджет и согласовать
  отдельно перед применением. Никаких RAM-хранилищ или специальных профилей.
- Существующие данные не удалять; нужные новые поля добавлять совместимо после согласования.

## 5. Как показывать на проекте

1. Обзор: показать три сервиса и объяснить их роли.
2. Swagger Payment: создать платёж → открыть его в списке и карточке.
3. HTTP: посмотреть контроллер Payment и клиент Antifraud; другой тип/сумма → другой результат.
4. БД: открыть сохранение и связь Customer–Payment; N+1 и JOIN FETCH показать в коде и API.
5. Redis: прочитать один ID, изменить платёж, прочитать снова; показать инвалидацию в коде/API.
6. Kafka: подтвердить платёж, увидеть Audit; повторить событие и увидеть отсутствие второй записи.
7. При необходимости поставить consumer на паузу и показать, что история догоняет после resume.

На экране один платёж и одно действие за раз. Автообновление списка не должно создавать
фоновую нагрузку во время замеров N+1/Redis во вкладке API.

## 6. Порядок внедрения после одобрения

1. Вернуть промежуточные файлы в согласованное состояние: оставить или откатить уже начатые правки.
2. Упростить UI и встроить Swagger; проверить запросы всех сервисов и недоступность одного из них.
3. Добавить согласованные типы/правила Antifraud и механику статусов.
4. Расширить события и историю Audit, проверить повтор без дублей.
5. Обновить примеры запросов и памятку сценария, выполнить тесты и браузерный прогон.

## Что уже затронуто до остановки

По ошибке начат рефакторинг common-libs, добавлены зависимости springdoc, переименованы служебные
lab пакеты/маршруты и их вызовы в UI/скриптах. Добавлен незавершённый тест Antifraud;
текущая сборка тестов на нём не проходит. Новые статусы/правила/Kafka-события, схема БД,
лимиты контейнеров и новый UI ещё не внедрены. Работающие backend-процессы не обновлялись
и не перезапускались; служебные пути в исходниках UI уже изменены, поэтому сейчас не совпадают
с запущенной версией backend. Это промежуточное, не готовое к использованию состояние.
Дальнейшие правки, включая выборочный откат, — после согласования с владельцем.
