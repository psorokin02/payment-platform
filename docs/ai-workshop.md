# Подготовка AI-блока на примере стенда

Это заготовки запросов и критерии проверки, а не выдуманная стенограмма успешного диалога.
Для проверки нужно сохранить фактически проведённый диалог и его результаты.

## AI для обучения: N+1

> Я изучаю Hibernate. В Payment есть LAZY-ссылка на Customer. Загружаю 12 платежей,
> затем читаю customer.getName() для каждой строки. Думаю, что всегда получится 13 SQL.
> Не давай готовый ответ. Задай один вопрос, который проверит моё понимание first-level cache,
> затем предложи маленький эксперимент с повторяющимся владельцем.

На стенде SQL виден в Сервисах → Логи → Payment. Ученик должен объяснить, почему количество зависит от разных
владельцев и какие данные нужны именно для этого представления списка.

## AI для разработки: инвалидация

> Прочитай PaymentCache и PaymentService. Сценарий: открываю NEW-платёж,
> подтверждаю, повторно открываю; Redis возвращает NEW, в PostgreSQL уже CONFIRMED.
> Предложи минимальную правку, которая удаляет кэш только после успешного commit.
> Объясни, какие гонки останутся. Проверь реальным циклом read → confirm → read;
> приведи команды и фактические результаты, не утверждай прохождение теста без запуска.

Рабочий путь: `PaymentService.confirmPayment` завершает запись через TransactionTemplate,
затем явно вызывает eviction и отправляет Kafka event через PaymentEventPublisher.
В Сервисах можно включить/выключить инвалидацию при включённом кэше,
а в Swagger посмотреть источник ответа: REDIS или POSTGRESQL.

Проверка: `node scripts/smoke.mjs`; отдельный тест называется
`Redis hit returns cached data; after-commit eviction returns CONFIRMED`.

При обсуждении показать и ограничения: cache-aside race, окно БД/Kafka без Outbox,
отличие гарантии локального INSERT/UNIQUE от exactly-once для всей системы.
