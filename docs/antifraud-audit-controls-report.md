# Antifraud, карточка платежа и идемпотентность Audit

Исторический отчёт до удаления replay и блокировок. Актуальная реализация описана
в [упрощённом потоке](simple-service-flow.md); нижеследующее сохраняет контекст прежней версии.

## Сделано и проверено

- При 503 от Antifraud — красная плашка «Невозможно создать платёж: система недоступна
  (Antifraud возвращает ошибку HTTP 503)». Платёж не добавляется, карточка успеха не открывается.
  Timeout и открытый Circuit объясняются отдельно, а не выдаются за полученный ответ Antifraud 503.
- Ручной повтор последнего события удалён из карточки, callback, frontend API-helper и стилей.
  Серверный replay API сохранён для совместимости проверочных скриптов. Отдельного действия
  «отменить последнее событие» в карточке не было. Кнопка случайных данных не добавлена.
- Во вкладке Сервисы Antifraud описывает реальный режим новой проверки: обычный ответ,
  постоянный 503, задержка 60 секунд с последующим 503 или принудительное отклонение платежей.
  Доступная админка больше не делает ошибочный бизнес-режим зелёным.
- Актуальная задержка slow — 60000 мс, затем 503 в контроллере; таймаут клиента — 900 мс.
  Обычная задержка и режим первых двух ошибок удалены по уточнению владельца 29 октября.
  При slow/timeout строка красная; при slow/retry или slow/breaker — предупреждение:
  повторная попытка может получить сохранённое решение без новой задержки.
  При reject HTTP доступен, а созданный платёж получает бизнес-статус REJECTED.

## Зачем блокировка платежа

Она защищает от двух одновременных подтверждений одного NEW-платежа.
Optimistic проверяет @Version; Pessimistic блокирует строку SELECT FOR UPDATE на время транзакции.
В обоих случаях только один запрос подтверждает платёж, второй получает 409.
Это демонстрация конкуренции в БД, не блокировка пользователю и не дедупликация Kafka.

## Audit: внедрено после явного согласования

27 октября владелец согласовал миграцию с сохранением данных. Она выполнена:
уникальность eventId перенесена в `audit_processed_events`, старые ID перенесены туда
до удаления только ограничения `audit_entries_event_id_key`. Первичный ключ фактов id сохранён.
DDL выполняется при старте Audit, внутри транзакции, а не на каждом переключении.

В Сервисах → Audit → Настройки Audit теперь единая форма: «Защита от дублей»,
«Обработка Kafka», «Сценарий ошибок» и кнопка «Сохранить настройки».
До нажатия кнопки изменения остаются черновиком; фоновые обновления его не сбрасывают.
У Payment и Antifraud такая же подпись кнопки сохранения. Логи переключаются четырьмя
кнопками вместо выпадающего списка. Первоначальный переключатель защиты заменён этой формой;
проверки ниже относятся к первоначальному этапу внедрения.
PUT `/admin/settings` принимает JSON `{ "idempotencyEnabled": true|false }`;
в UI это `/api/audit/admin/settings`. GET `/admin/status` возвращает фактическое значение.
UI проверяет отдельное чтение и обновление состояния, прежде чем подтвердить сохранение.
По умолчанию защита включена. При пяти копиях:

- включена — пять доставок, один сохранённый факт;
- выключена — пять доставок, пять фактов с одинаковым eventId;
- включена обратно — старые дубли остаются, новые эффекты уже встречавшегося события не добавляются.

Отметка eventId и INSERT факта составляют одну транзакцию. При ошибке обе записи откатываются.
Журнал eventId пополняется и без защиты. Режим фиксируется в начале каждой обработки;
переключение не меняет уже обработанные или начавшиеся доставки.
Рестарт берёт значение `app.audit.idempotency-enabled` из YAML (true).

### Сохранность данных

- До миграции остановлен только Audit. Архив всей БД:
  `.runtime/audit-before-idempotency-20261027.dump`, 33 КБ; проверен полным чтением через
  `pg_restore --file=/dev/null`. Восстановление в БД не выполнялось.
- Все прежние 229 строк с id ≤255 сохранены: хеш значений всех полей до и после
  `6e6e86af4d853e5d7acb2ceae10cc9c2` совпал. В журнал перенесены все 229 eventId.
- После испытаний повторный старт сохранил все 286 строк на тот момент:
  хеш `24289f9dbb35e8f6322727966a08dfc1` также совпал. Выключенная runtime-защита
  после рестарта вернулась к true. Повторный запуск миграции безопасен.
- Kafka продолжила с committed offset256 (DLT4), сброс offsets не выполнялся.
  Повторный прогон после рестарта прошёл; учебные записи добавлялись, старые не удалялись.
- Исходники до изменения сохранены в `.runtime/before-audit-idempotency-20261027.tgz`.
  Папка не является Git-репозиторием; Git не инициализировался. Простое возвращение старого
  JAR не откатывает схему: после создания дублей возврат старого UNIQUE требует отдельного
  согласованного плана. Предмиграционный архив не содержит более поздних учебных записей.
