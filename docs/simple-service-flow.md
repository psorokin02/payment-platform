## Актуальные настройки кэша и удаление диагностики

`cacheMode` заменён двумя независимыми флагами: `cacheEnabled` и `cacheInvalidationEnabled`.
Оба включены по умолчанию. В UI это отдельные списки «Кэш Redis» и «Инвалидация кэша».
`confirmPayment` после commit вызывает `PaymentCache.invalidatePaymentCache`, внутри которого
проверяется флаг инвалидации. При смене флагов очистка Redis завершается до применения настроек;
ошибка очистки не оставляет частично применённых настроек.

Удалены deliveries/duplicates из Audit, calls из Antifraud и attempt из AntifraudCheckResponse.
Для проверки доставок и retry используются обычные логи с requestId/eventId, а не счётчики API.

Сохранены правки владельца: Lombok в PaymentSettings, имя processPaymentEvent, ранняя ветка
при выключенной идемпотентности, форматирование listener и fallback requestId в Antifraud.
При выключенной защите журнал не пополняется: первая доставка старого неотмеченного eventId
после включения может добавить один факт. Существующие дубли не удаляются.

requestId генерирует Payment-клиент один раз на проверку и сохраняет во всех retry.
Antifraud генерирует его только для прямого запроса без ID либо с пустым ID (например, Swagger).
Переданный ID не заменяется; это ID проверки, не ID платежа.

## Предыдущий этап: publisher, Antifraud и Hibernate

`publishEvent` сериализует событие один раз и вызывает `sendCopy` в коротком цикле.
Результат ACK логируется отдельным `logSendResult`; синхронный сбой одной копии не мешает другим.

Antifraud: normal/reject/error/slow. Режим первых двух ошибок удалён. В бизнес-сервисе нет sleep:
после проверки входных данных и существующего requestId выполняются ранние решения
FORCED_REJECTION → RISK_LIMIT → APPROVED. Контроллер имитирует HTTP-сбой: сразу 503 либо
пауза 60000 мс и затем 503 без записи проверки. Обычная искусственная задержка удалена.
Убраны аннотация Operation и её пример над методом; OpenAPI генерируется из маршрутов/DTO.

Audit: удалены retry/DLT, имитация ошибок, старые счётчики и API fail-next. UI содержит только
защиту от дублей и паузу. CommonLoggingErrorHandler явно логирует и пропускает ошибочную запись;
это исключает неявные повторы стандартного error handler. Перезапуск/повторная доставка брокера
всё ещё возможны, поэтому журнал идемпотентности сохранён.

Репозитории Audit и Antifraud переведены с JdbcTemplate на Hibernate/Spring Data JPA.
История читается через Query, факт сохраняется через save. Отметка eventId и факт остаются
одной транзакцией. MarkProcessed и вставка Antifraud используют nativeQuery с ON CONFLICT DO NOTHING.
Таблицы, данные и SQL начальной схемы не менялись; ddl-auto=none у Audit/Antifraud.
JdbcTemplate в тестах используется только для независимой проверки фактических строк БД.

## Запись и Kafka

Путь в коде теперь прямой:

1. `PaymentService.createPayment` вызывает Antifraud по HTTP.
2. `TransactionTemplate.execute` записывает платёж и завершает commit.
3. `PaymentService` напрямую вызывает `PaymentEventPublisher.publishEvent`.
4. Publisher сериализует одно событие и отправляет его через обычный `KafkaTemplate.send`.
5. Результат каждой публикации попадает в лог через `whenComplete`.

При подтверждении сначала выполняется UPDATE/commit, затем вызов invalidatePaymentCache
и публикация нового события. При cacheInvalidationEnabled=false инвалидация намеренно пропускается.
Локальные `PaymentCommitted`, `PaymentCommitListener` и `ApplicationEventPublisher` удалены.
Kafka listener в Audit сохранён: это получатель сообщений брокера, а не промежуточное событие Spring.

Операция записи владеет отдельной транзакцией (`REQUIRES_NEW`). Если вызывать её из другого
транзакционного сценария, внешний rollback не отменит уже закоммиченный платёж. Текущие входы —
нетранзакционные HTTP-контроллеры. Вызовов HTTP и Kafka внутри собственной транзакции записи нет.

`send` не ожидает ACK отдельным `get`: успешный HTTP-ответ означает сохранённый платёж,
а не гарантированную доставку в Audit. Сам `send` может кратко ждать metadata/буфер
согласно `max.block.ms`. При ошибке Kafka платёж остаётся в БД, ошибка записывается в лог.
Без Outbox PostgreSQL и Kafka не образуют одну атомарную операцию.

Сохранена настройка `eventCopies=1…5`: у копий одинаковые eventId, key и JSON.
Ручной replay API не восстанавливался; живые проверки используют эту настройку.

## Последующее упрощение HTTP-клиента Antifraud

В `AntifraudClient` удалён локальный AtomicInteger-счётчик попыток. `checkPayment` выбирает
прямой вызов с таймаутом либо `callWithRetryAndBreaker`. Один requestId сохраняется на все повторы.
Короткий `sendRequest` последовательно вызывает `createRequest`, `executeRequest` и `readDecision`.
Сетевые исключения обрабатываются в одном месте; таймаут и ошибка соединения используют общий catch,
прерывание потока сохраняет interrupt-флаг. Некорректный ответ остаётся 502 без retry.

Проверка 5xx теперь числовая: код 599 больше не вызывает IllegalArgumentException из поиска enum.
Регрессия воспроизведена тестом с настоящим HTTP-сервером до исправления, затем тест прошёл.
После этой правки `make test`: 25 скриптов + 89 Java + 55 UI = 169 успешно.
JAR Payment пересобран, только Payment перезапущен; health=UP и административный API отвечает.
